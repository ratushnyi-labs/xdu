# Contributing to xdu

Contributions are welcome. This document describes how to contribute effectively.

## Development Setup

1. Install [Docker](https://docs.docker.com/get-docker/) — all builds and tests run in
   containers per the project's host-isolation rule.
2. (Optional) Install Rust via [rustup](https://rustup.rs/) for editor integration.
   The container provides a pinned toolchain; the host install is purely a convenience.
3. Clone the repository:

   ```sh
   git clone https://github.com/ratushnyi-labs/xdu.git
   cd xdu
   ```

4. Run the dev verifier:

   ```sh
   docker compose run --rm test sh -c "cargo fmt --all -- --check \
     && cargo clippy --all-targets --all-features --locked -- -D warnings \
     && cargo test --locked"
   ```

5. Run a release build:

   ```sh
   sh scripts/build.sh
   ```

## Workflow

1. Fork the repository.
2. Create a feature branch from `main`: `git checkout -b feat/my-feature`.
3. Make your changes.
4. Run the dev verifier (above) and a representative release build.
5. Commit with a message that includes the backlog item ID (see "Commit Messages" below).
6. Open a pull request against `main`.

## Code Style

- Max line width: **120 characters**.
- No dead code, TODO comments, or commented-out logic.
- `///` doc comments on every new public function and public type.
- Follow Rust naming conventions: `snake_case` functions, `CamelCase` types,
  `SCREAMING_SNAKE` constants.
- Max function length: **30 non-empty, non-comment lines**. Extract when over.
- Max type/`impl` block: **500 non-empty, non-comment lines**. Split when over.

## Safety Rules

xdu inspects filesystem metadata and performs two opt-in mutating actions
(file/directory delete and Windows foreign-handle force-close). All contributions
MUST follow these safety rules:

- **Read-only by default (BR-001).** The mutation paths are *exactly* (a) `d` delete
  via `App::perform_delete`, (b) `f` force-close via
  `lock_detect::force_close_handles_for_path` from inside the lock-prompt, and (c) the
  explicit JSON export file write. **No other code path may mutate the filesystem.**
- **No process termination.** `OpenProcess(PROCESS_DUP_HANDLE)` is the only foreign-process
  call. `TerminateProcess` and direct `NtClose` on a foreign handle are forbidden.
- **`unsafe` blocks are small and labelled.** Every `unsafe` block carries a
  `// SAFETY:` comment explaining the preconditions. New `unsafe` requires
  ADR amendment if it adds a new external library link beyond `kernel32`, `ntdll`,
  `rstrtmgr`, or `libc`.
- **Bounds and overflow.** Use checked or saturating arithmetic on size sums; never
  index into a `Vec` without a prior `get` or bounds check; never `unwrap()` on data
  derived from the filesystem or from user input.
- **Resource hygiene.** Pair every opened handle / session with a `Drop` guard or
  paired `Close*` call on every exit path. Lock guards are held for narrow scopes —
  never across a `term.draw` cycle longer than one frame.
- **Path validation on writes.** Refuse `\0` bytes, refuse `..` segments outside the
  scan root, refuse writes into `/proc`, `/sys`, `/dev` on Unix.

## Testing Requirements

- All existing tests MUST pass before submitting a PR
  (`cargo test --locked` inside the dev container).
- New features MUST include tests: positive + negative + security/adversarial paths.
- Security tests use the `test_sec_uc###_*` naming convention so they are easy to
  enumerate (`grep -r 'fn test_sec_uc'`).
- Coverage target is **100% lines + functions** on the library crate, enforced via
  `cargo-llvm-cov --fail-under-lines 100 --fail-under-functions 100`.
- Tests live in colocated `#[cfg(test)] mod tests` blocks (unit) and in
  `tests/integration_test.rs` (integration). TUI snapshot tests are added when the
  `LATER-004` harness lands (TASK-007-F).

## Commit Messages

xdu uses a backlog-item-prefixed convention rather than strict Conventional Commits.
This makes it easy to trace a commit back to its backlog file under `docs/backlog/`:

- `TASK-###: <subject>` — for `TASK` items.
- `TASK-###-X: <subject>` — for sub-tasks (X is the suffix).
- `BUG-###: <subject>` — for `BUG` items.

The subject is a short imperative phrase. Long bodies are encouraged when the change
is non-trivial. **Never include agent / model / vendor attribution** in commit
messages (no `Generated by`, no `Co-authored-by:` trailers for an AI agent).

## PR Checklist

Before submitting a pull request, verify:

- [ ] `cargo fmt --all -- --check` clean
- [ ] `cargo clippy --all-targets --all-features --locked -- -D warnings` clean
- [ ] `cargo test --locked` passes
- [ ] `sh scripts/build.sh` produces all targets within the size budget
- [ ] No `unsafe` block without a `// SAFETY:` comment
- [ ] No new crate dependency without an ADR amendment
- [ ] No agent attribution in commits or co-author trailers
- [ ] Backlog item updated (`docs/backlog/`); Speck updated (`docs/specks/`) if applicable
- [ ] CHANGELOG.md updated under `## [Unreleased]` with one line per user-visible change
